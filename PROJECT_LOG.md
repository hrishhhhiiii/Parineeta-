## 2026-09-28 · Fix: raw unstyled page flashing before the site loads

**Reported:** on every load and refresh, before the site appeared, the browser showed the page as raw HTML — blue underlined links, no layout, and a giant black circle at the top.

**Cause (not caused by the restructure; latent since the preloader was added):** in dev, Vite injects `main.css` from JavaScript (`main.js` imports it), so the first paint has no CSS at all. The preloader was meant to cover that moment, but it is styled by that same `main.css`, so it was unstyled too. The black circle was the preloader's SVG ring rendered at full width with the browser's default black fill. The production build was not affected: there the CSS is a render-blocking `<link>` in `<head>`.

**Fix:** a small inline `<style>` in the `<head>` of `frontend/index.html` that mirrors only the preloader's rules from `src/styles/main.css`: the brand background, the fixed full-screen preloader, the gold ring and its draw animation (same `cubic-bezier(0.16, 1, 0.3, 1)` easing as `main.css`, so it does not restart when the full stylesheet takes over), and the 5-second failsafe that hides the preloader even if JavaScript never runs.

**Verified in headless Chrome:** with the JS entry blocked (frozen at first paint), the page shows the gold ring drawing on the brand background instead of raw HTML, and the failsafe hides the preloader after 5.6s. On a normal load the preloader is removed, fonts load and there are no console errors. The inline block is present in the built `dist/index.html` and in the generated product pages.

**Not changed:** `admin.html`, `login.html` and `account.html` have no preloader and no inline styles, so they can still show a brief unstyled flash in dev. They were not part of the report.

## 2026-09-28 · website/ restructured into frontend/backend/database

**Status:** done. Verified with `npm run build` (all 4 entry points + 14 product pages) and `node --test test/cms.test.mjs` (7/7 pass) after every change, both run exactly as CI runs them.

**Context.** By this point `website/` had grown far past the static site from 09-25/26: a separate editor had added a Supabase-backed CMS, an admin panel, customer accounts, sign-in, and a live GitHub Actions pipeline (`.github/workflows/publish.yml`) deploying to Cloudflare Pages or SFTP on every push to `main`. `website/` turned out to be its own git repo (remote `github.com/hrishhhhiiii/Parineeta-`), nested inside the outer `logo/` repo. None of this existed when the redesign log entries above were written.

**Decision.** The app has no server of its own — the browser talks to Supabase directly (RLS-protected) for everything except sending an enquiry, which goes through one edge function. So "backend" and "database" aren't pre-existing layers, they're a boundary I had to choose. Asked the owner; picked the full 3-way split: `frontend/` = the whole Vite app, `backend/` = the one edge function, `database/` = the SQL migrations and schema. `scripts/`, `test/`, `docs/`, and the deploy/CI config stay at `website/` root, because they reach into more than one layer (e.g. `cms-schemas.mjs` reads a frontend file and writes a database migration) — forcing them into one folder would have meant uglier cross-folder relative paths for no real benefit. Not taken: also moving `scripts/` into `backend/` (rejected for that reason), and a narrower split that left the Vite app flat (rejected — the owner wanted the full split).

### A mistake made and caught during this pass
The first attempt at the doc path-fixes used a plain Python `open(path, "w", encoding="utf-8")` on Windows, which silently translates every `\n` to `\r\n` on write. The docs were CRLF-committed but the *change* was meant to touch ~6 lines each; instead every line in 7 files came out as "changed" (a ~90-line diff for a 6-line fix). Caught it by noticing `git diff --stat` was reporting far more churn than the edits justified, confirmed the cause with `od -c` against the git blob, reset the affected files with `git checkout --`, and redid the substitution with `newline=""` on both the read and the write so line endings pass through untouched. Diffs are now proportionate to the actual content change.

## 2026-09-27 · Indexable product pages

Product pages were hash routes (`#/p/<id>`), so search engines and link previews saw the whole site as one page.

- **Prebuilt pages:** a build plugin, `build/product-pages.js` (registered in `vite.config.js`), writes `dist/p/<id>/index.html` for all 14 products. Each is the normal site with that product's title, description, `og:*` tags (`og:type` product, the product photo or reel still as the image) and static Product JSON-LD. Sets are skipped, as before.
- **Router:** `src/ui/router.js` now also opens a product from the path `/p/<id>/`. The hash form still works and is still used for in-page links. Any other hash on a product path, such as `#collection`, rewrites the URL to `/#collection` and shows the landing page. Prebuilt pages carry the landing title and description on `<html data-landing-title/-desc>`, so leaving a product restores them.
- **Share links and JSON-LD `offers.url`** now use `/p/<id>/`. (`ui/productPage.js`)
- **`VITE_SITE_URL`** (added to `.env.example`): when set at build time, the home page and product pages get `<link rel="canonical">`, `og:url` and absolute `og:image`/JSON-LD image URLs, and `dist/sitemap.xml` lists `/` plus the 14 product pages. When it is empty, pages are still built and URLs stay relative. The build also writes `robots.txt` with `Disallow: /admin` and, when the site URL is set, a `Sitemap:` line.
- **Verified:** without and with `VITE_SITE_URL=https://example.test`, each page has exactly one canonical link and the right image. In headless Chrome, on both the production build and the dev server: a direct `/p/shola-mukut/` opens the product with its title; an `#collection` link returns to the landing title; the `#/p/gach-kouto` route and browser Back work; an unknown `/p/…` falls back to landing. Full audit rerun at 1440, 375 and reduced motion: zero console errors, no missing files, no sideways scroll.
- **To do at launch:** set `VITE_SITE_URL` in the Vercel project settings, then submit `sitemap.xml` in Google Search Console. Products added later through the admin panel (Supabase) get no prebuilt page until the next build, but still open through the hash route.
